## 🎤 第二幕：为什么做这个项目（3 分钟）

### 演讲稿

> 我先说说为什么要做这个项目。其实就三点。

> **第一，市面上的网盘，要么收费，要么限速。** 大家都用过百度网盘吧？不充会员下载速度只有几十 K。而且你的文件存在别人的服务器上，你真的放心吗？照片、文档、工作文件，这些都是很隐私的东西。
>
> **第二，AIGC 火了，但大多数云盘跟 AI 还是割裂的。** 你有没发现，你存在网盘里的文件，跟你用的 AI 工具完全是两套系统？你要先下载文件，再上传给 AI，中间绕了好几道。我想能不能把 AI 直接嵌到网盘里？你存了文件，顺便就能让 AI 帮你读、帮你分析。
>
> **第三，我刚好想练手 Go 语言。** 我之前主要写 Java，Go 是自学的。我觉得学一门新语言最好的方式就是用它完整地做一个项目，从数据库设计到 API 开发到部署上线。
>
> 这三个原因加在一起，就有了 AiDisk。

## 🎤 第三幕：技术架构（5 分钟）

### 演讲稿

> 好，我们来看看架构。
>
> （翻到架构图页面）
>
> 整个项目分三个部分：**Agent 服务**、**AI 服务**和**前端 Web**。
>
> Agent 服务是核心，负责所有文件相关的操作 —— 上传、下载、分享、回收站，以及用户注册登录。它是用 Go 的 Gin 框架写的，总共 27 个 Go 文件，暴露了 50 多个 API 端点。数据库用的是 MySQL，文件存储用的是 MinIO —— 这是一个兼容 S3 协议的对象存储，开源免费。
>
> AI 服务是后来加的，专门处理 AI 相关的请求。它基于字节开源的 Eino Agent 框架，实现了聊天、文档分析、网盘智能查询三个 Agent。它用 Redis 存聊天历史，用 MySQL 存对话记录，支持同时接 Ollama 本地模型和 OpenAI 兼容的云端模型，而且可以运行时动态切换。空载的时候只占 55MB 内存，相当轻量。
>
> 前端是用 Vue 3 + TypeScript 写的，UI 组件库用的 Element Plus。我花了很大精力做了响应式适配，从 375px 的手机到 1440px 的桌面都能正常用。前后端通信全部走 RESTful API，认证用的是 JWT。
>
> 部署方面，整套服务跑在一个 4 核 4GB 的轻量云服务器上，用 Docker Compose 编排。服务器上跑了十几个容器 —— MySQL、Redis、MinIO、Elasticsearch、RabbitMQ，加上我们的 Agent 和 AI 服务。内存用了大概 2GB，CPU 平时只有 1-2%，4GB 的服务器跑起来绰绰有余。
>
> （翻到下一张图，展示服务间通信）
>
> 这里有一点值得讲：Agent 服务和 AI 服务共享同一套 JWT 认证。用户在 Agent 登录拿到的 Token，直接就能用来调 AI 服务的接口，两个服务用相同的密钥解析。这就保证了用户体验是连贯的 —— 你登录了一次，接下来的所有操作都不需要重新认证。
>
> 好，架构就讲到这。接下来我给大家演示一下实际效果。

## 🎤 第五幕：深入技术亮点（5 分钟）

### 演讲稿

> Demo 看完了，我来深入讲几个技术实现上的细节。这些可能对在座做后端或全栈的同学比较有用。
>
> **第一个亮点：分块上传。**
>
> （翻到分块上传流程图）
>
> 大文件上传是个经典问题。如果你直接把一个 1GB 的文件用 HTTP POST 发到服务器，中间的网关、Nginx、后端都有大小限制，而且一旦断了就得重来。
>
> 我的方案是这样的：前端先把文件切成 5MB 一块，然后调用初始化接口，后端返回一个文件 ID。接下来前端一块一块上传，每块带自己的编号。后端收到之后暂存到 MinIO，最后调用合并接口，后端把所有分块拼成完整的文件。
>
> 这里面有一个巧妙的点：秒传。上传之前先算一下文件的哈希值，如果服务器上已经有了，直接返回成功，一秒都不需要。
>
> （翻到下一页）
>
> **第二个亮点：AI Agent 的设计。**
>
> AI 服务用了三个 Agent：聊天、文档处理、网盘查询。每个 Agent 有自己的系统提示词和工具集。比如 PanAgent 接到"查看我的存储空间"这句话，它会先做意图识别 —— 是查空间、查文件列表、还是查文件统计 —— 然后对应地查询数据库，最后把结果返回给 LLM 生成自然语言回答。
>
> 我还做了一个 Agent 池，把常用的 Agent 实例缓存起来复用，避免每次请求都重新创建 LLM 客户端。这个优化把平均响应时间降低了大概 30%。
>
> （翻到下一页）
>
> **第三个亮点：Token 追踪。**
>
> 调用 AI 接口是要花钱的，所以我加了一个 Token 统计系统。每个用户每天、每小时用了多少 Token 都记录在 Redis 里，前端可以实时看到。如果超出限额，API 直接拒绝，防止单个用户把额度用完。
>
> 还有一个上下文裁剪机制：对话长了之后自动截断，只保留最近的 N 条消息和一份历史摘要，既控制了 token 消耗，又不至于让 AI 完全"失忆"。
>
> （翻到下一页）
>
> **第四个亮点：部署架构。**
>
> 我用 Docker Compose 把整个项目编排成一个服务栈。好处是：在任何机器上，只要装好 Docker，一条命令就能跑起来。不会有"在我机器上能跑，在你机器上跑不了"的问题。
>
> 而且我做了内存优化。MySQL 的 buffer pool 限制在 64MB，Redis 的最大内存限制在 32MB，MinIO 也调了小内存模式。整套服务跑在 4GB 的服务器上，内存使用不到 2GB，CPU 长期 1-2%。非常省资源。
>
> （翻到下一页）
>
> **第五个亮点：Eino 生产级实践。**
>
> 这部分我特别想单独说一下。AI 服务底层用的是字节开源的 **Eino** 框架，这是一个 CloudWeGo 出品的 AI 应用开发框架。AiDisk 应该算是 Eino 在生产环境里比较完整的实践案例之一 —— 不是 demo、不是 example，是真实跑在线上、有真实用户在用的。
>
> （指 PPT 上的 GitHub 链接和 Demo 链接）
>
> 代码在 GitHub 上开源，线上有可访问的 Demo：pan.aqi125.cn，大家可以现场扫码体验。
>
> 我具体怎么用 Eino 的？主要有四个层面：
>
> **第一，用 Eino 的 ChatModel 抽象做 LLM 多后端切换。** 我后端同时接了 Ollama 本地模型和 DashScope 云端模型，两个 provider 都实现了 Eino 的模型接口。运行时调一个 API 就能切换，不用重启服务。这套机制完全是 Eino 提供的，我只需要写适配层。
>
> **第二，用 Eino 的 Agent 抽象做了三个 Agent。** 聊天、文档处理、网盘查询，每个都是独立的 Agent 实例，有自己的系统提示词和工具集。PanAgent 那个意图识别的玩法，就是基于 Eino 的 Agent 接口扩展出来的。
>
> **第三，用 Eino 的 Callback 机制做 Token 统计。** Eino 提供了一套回调钩子，我在每条 LLM 调用前后埋点，把消耗的 token 数记到 Redis，前端实时展示。这个机制的好处是侵入性极低，业务代码完全不用改。
>
> **第四，用 Eino 的 Stream 接口做 SSE 流式输出。** 聊天和文档分析都是流式的，前端能一个字一个字看到 AI 的回答。Eino 的 Stream 接口把底层的 chunk 处理封装好了，我只要 Recv 循环读就行。
>
> 生产环境也踩了一些坑。最大的一个是长对话的上下文管理。一开始对话超过 20 轮，token 直接爆掉。后来用了 Eino 的 `TrimMessages` 函数，配合自己写的摘要机制 —— 超过阈值就把旧对话压成一份摘要塞回系统提示词里。这样既控制了 token，AI 又不会"失忆"。
>
> 还有一个是并发调用的资源管理。文档分析有时候要并行处理多个 chunk，每个 chunk 都会创建一个 LLM 客户端，并发一高就把内存吃光了。我做了个 Agent 池，复用客户端实例，并发上限也做了控制。这个优化把平均响应时间降了大概 30%，内存峰值降了 40%。
>
> （翻到下一页）
>
> 所以如果你们团队也在考虑用 Eino 做 AI 应用，AiDisk 的代码可以作为一个参考。我把生产环境踩的坑都写在了代码注释里，希望能帮大家少走点弯路。
>
> 好，技术亮点就讲到这里。

### 备用 Q&A

**如果没人提问，你可以自己引导：**

> 我猜可能有人想问：为什么用 MinIO 而不是直接用阿里云 OSS 或 AWS S3？
>
> 因为 MinIO 是 S3 兼容的，代码不用改，而且自部署不花钱。将来如果想切到云厂商的对象存储，只需要改一行配置。

> 也可能有人好奇：为什么不把 Agent 和 AI 两个服务合并成一个？
>
> 确实可以合并，我也考虑过。分开的好处是：AI 服务如果因为模型调用耗时太长影响了响应，不会拖慢文件上传下载。不过我分析过了，4GB 服务器上跑两个 Go 服务，内存多占 50MB 左右，CPU 几乎没差别，暂时先保持现状。

> 也可能有人对 Eino 感兴趣：为什么选 Eino 而不是 LangChainGo？
>
> 两个都看过。LangChainGo 是 LangChain 的 Go 移植，但维护活跃度一般，而且很多 Python 那边的特性在 Go 这边缺失。Eino 是字节原生 Go 写的，组件化设计更彻底，回调机制和流式接口也更符合 Go 的风格。最关键的是 Eino 有 CloudWeGo 团队在持续维护，长期看更稳。

> 可能有人会问：Eino 在生产环境踩过什么坑？
>
> 最大的坑是 ChatModel 的并发管理。Eino 的模型客户端默认不是协程安全的，多 goroutine 同时调用同一个实例会出问题。我做了个 Agent 池，每个实例加锁，或者从池里取不同实例。另外 Eino 的 stream 接口在异常时需要显式 Close，不 Close 会泄露连接，这个我也踩过。
